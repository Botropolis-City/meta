# First launch after item 159, against r873, 2026-10-22

**Rig:** Intel Core Ultra 7 265U, 14 threads, 62 GiB; integrated Arrow Lake-U GPU (not used: no city was opened); 1920×1200, i3 on X11, Arch Linux, kernel 7.2.
It is the machine of [the item 157 report](2026-10-21-ultra7-265u-igpu-item-157.md), and every figure is judged against the *First launch* budgets in [budgets.md](../budgets.md).
**Builds:** r873 (`be5360c`), item 157's slice 1 and the baseline item 159 was filed against; r898 (`a6bbb78`), item 159's four slices on top of items 196, 197 and 162, which landed between; each built with `go build ./cmd/botropolisd` from `git archive`, go 1.27.3.
**History on disk:** 213 transcripts, 3,312 MiB, 147 projects, 11 written in the last hour, 27 `claude` processes running, item sessions among them.
**Runs:** cold start (until idle, at 1 s) with both builds side by side, then quit-and-relaunch: both cold again, each sent `SIGTERM` at 60 s and started again on its own state, sampled until idle.
Both runs held `/tmp/botropolis-land.lock`, so no landing's test suite shared the cores; the load average was 10 at the start and 3 at the end.
Every daemon had an empty state directory, socket, runtime and config directory of its own and a stub `claude`; `~/.claude` was only read.

## Findings

1. **The first read no longer takes the machine.** From 10 s to idle, r898's paced ingest held 48–55% of a core in every 1 s sample; r873 had 28 samples over 100%, scattered through its first 42 s (cold start).
   In all, 44.6 CPU-seconds against 47.4, and r898 was idle at 172 s against 210 s, because items 196 and 197 cut the rescans' work in the same span.
2. **The first 9 s still exceed one core**: 8 samples at 100–112% for r898, while the daemon's first load reads a window of every stored transcript and every live transcript whole, at about 100 MiB/s, before any paced pass starts (cold start).
   The budget is ≤ 1 core in all, so this misses it by 12% of a core for 9 s, once.
   The synthetic home of `TestFirstLaunch` has few transcripts, so its first load is instant and the suite could not see this.
   The same 9 s keep the first map back past the budget's 5 s; item 159's opening panel shows "Reading your sessions · N of M" meanwhile instead of an empty window.
   Making that load smaller, which serves both budgets, is [item 203](../../roadmap/203-the-first-load-runs-unpaced-before-the-map.md).
3. **A quit part-way loses the first load, not the read**: killed at 60 s, r898 had read 2,680 MiB and read 2,144 MiB after relaunch, 4,825 MiB in all against 4,010 MiB uninterrupted (quit-and-relaunch).
   Of the 815 MiB more, about 750 MiB is a second first load (r873's relaunch, whose ingest had all but finished, read 750 MiB), so the ingest itself read about 64 MiB twice, a few 16 MiB checkpoints' worth.
   0.2.2 relaunched read 89% of an uninterrupted run again; r898's relaunch read 53% of one, nearly all of it either new or the first load.
4. **Memory is far under budget**: r898 peaked at 53 MiB of `Private_Dirty` against ≤ 256 MiB, r873 at 38 MiB; r898's live heap peaked at 14 MB, with 205 collections against r873's 479 (cold start).

## What it does not show

- **The city.** No window was opened; the city's side of the first launch (the reading bar, the opening panel, the CPU it spends before it draws) is gated by `TestFirstLaunchCity` and `TestFirstLaunchCityWaiting` on synthetic history, and by Aria's judgement of two frames.
- **macOS.** Background priority there is unmeasured and is [item 200](../../roadmap/200-first-launch-runs-at-full-priority-on-macos.md).
- **Statistics off.** Both builds ran with the config's statistics on; with them off the whole read is paced the same way and a relaunch reads stopped transcripts whole again, by decision (item 159's deviations).
- **A reference machine.** Like every report so far, this is a 14-thread laptop, not the 4-core minimum; on 4 cores the first load's 9 s are a larger share of the machine.
- **Separation of the rescans' gains from this item's.** Items 196 and 197 landed between r873 and r898, so the end-to-end time and CPU-seconds are theirs and this item's together; the per-second shape (half a core from 10 s on) is this item's.

## Reproduce

```sh
mkdir -p /tmp/r873 && git -C botropolis archive be5360c | tar -x -C /tmp/r873
(cd /tmp/r873 && go build -o botropolisd ./cmd/botropolisd)
mkdir -p /tmp/r898 && git -C botropolis archive a6bbb78 | tar -x -C /tmp/r898
(cd /tmp/r898 && go build -o botropolisd ./cmd/botropolisd)
flock /tmp/botropolis-land.lock performance/tools/perf-daemon-ab --cold --seconds 1500 --interval 1 r873=/tmp/r873/botropolisd r898=/tmp/r898/botropolisd
```

The quit-and-relaunch comparison started both daemons as `perf-daemon-ab --cold` does, sent each `SIGTERM` at 60 s, read `rchar` from `/proc/<pid>/io` just before, started each again on the same state directory and sampled it with `performance/tools/perf-sample --until-idle 60`.
